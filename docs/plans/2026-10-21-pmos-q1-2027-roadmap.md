# PM OS — Q1 2027 Roadmap for 12Labs (plan)

## Context
Jay wants a reusable **PM operating system**: take customer and sales signals, derive backlog items from them, rank the items with RICE, and lay out a Jan–Mar 2027 roadmap. The first example company is the **fictional 12Labs voice/audio product** that already lives in this repo (FastAPI + Chroma RAG over 36 mock voice-agent interviews, `data/transcripts/call_*.json`).

Most of the inputs don't exist yet. Three source types still need to be invented as realistic mock data: sales/CRM feedback, Fireflies meeting notes and contractual deal-breakers. ## Derivation skill: `.claude/skills/derive-backlog/SKILL.md`
**Steps:**
1. Read every source file for the chosen company.
2. Pull out requests and pain points, each tagged with its source record ID.
3. Group them into backlog items.
4. For each item, write: `{id, title, problem, squad, evidence:[{source, record_id, account, quote}], suggested:{impact, confidence, effort_pw, rationale}, depends_on[], commitment_id?}`.
5. Write `derived/backlog.json`.
6. Run `python -m pmos.validate` and fix anything that fails.
7. Append a `backlog.derived` event.

**Rules:**
- Every item must have at least one evidence quote, and each quote must exist word for word in its source (the validator checks this).
- Commitments always become items with `commitment_id` set.

## RICE and scheduling (`pmos/rice.py`, `pmos/scheduler.py`)
- **Reach:** the sum, over the distinct accounts in an item's evidence, of `clamp(arr/median_arr, 1, 3)`. Raw account count and total ARR are shown next to it. Reach is computed, never typed in.
- **Score:** `R × I × C / E`, using overrides where they exist and Claude's suggestions otherwise. Impact is on the 0.25–3 scale, Confidence is 0.5/0.8/1.0, Effort is in person-weeks.
- **Scheduler:**
  1. Commitments go into the earliest month on or before their due month where their squad has room. If none fits, flag "at risk".
  2. Everything else goes in by score, highest first: the earliest month where `depends_on` is already scheduled earlier and the squad has capacity.
  3. Items bigger than one squad-month are flagged so Claude can split them.
  4. Whatever doesn't fit goes in "below the line".
- **Month themes:** derived from the dominant theme in each month's items, editable.

## State (`pmos/state.py`) and build tracking
- **`events.jsonl`:** append-only, one line per event: `{ts (ISO-8601 UTC), actor ("claude"|"user"), type, payload}`.
- **Event types:** `sources.loaded`, `backlog.derived`, `item.updated`, `item.merged`, `item.dropped`, `roadmap.built`, `roadmap.exported`.
- **`snapshot.json`:** rebuilt by replaying events over `backlog.json`. Overrides are stored by item ID, so they carry over when the backlog is re-derived.
- **`STATE.md`:** a timestamped session log (done / in progress / next / blockers) that Claude updates at the end of each session.
- **`FEATURES.md`:** each feature has an ID and status, and only moves to done after verification passes.

## API and UI
- **API:** `GET /api/pmos/sources`, `GET /api/pmos/backlog`, `PATCH /api/pmos/items/{id}`, `POST /api/pmos/items/merge`, `DELETE /api/pmos/items/{id}`, `POST /api/pmos/roadmap/build`, `GET /api/pmos/roadmap`, `GET /api/pmos/roadmap.md`, `GET /api/pmos/events`.
- **Sources page:** record counts, a filterable list of records, and the events timeline.
- **Backlog/RICE page:** a sortable table with inline-editable I/C/E. Reach is read-only and shows how it was calculated. Includes merge, drop and an evidence drawer.
- **Roadmap page:** Jan, Feb and Mar 2027 columns, each with a theme, a capacity bar per squad, item cards and the Committed badge. Below the columns: the "below the line" list and an Export ROADMAP.md button.
